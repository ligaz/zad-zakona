# Data pipeline — как се извличат данните (само сверени факти)

Принцип: в `data/` влиза само сверено с първичен източник
(parliament.bg API, стенограма, Държавен вестник). Без измислени данни —
`verified: true` означава проверено, не попълнено.

## Източници

### parliament.bg API (`https://www.parliament.bg/api/v1`, header `User-Agent`, ~1 req/s)
- `/act/{id}` — акт: заглавие, сигнатура, ДВ брой/година, **пълен текст от ДВ**
  (`L_ActL_final_body`: указ, дати, президент, параграфи), `L_Act_date2` = дата
  на приемане. ВНИМАНИЕ: `L_Act_dv_ID` е ID на **броя** в ДВ, не на материала!
- `/bill/{id}` — законопроект: `imp_list` (депутати-вносители; празен = МС или
  обединен), `union_label` (обединен), `steno_hall` (точните стенограми за
  I и II гласуване: `Pl_Sten_id` + `L_Act_St2_name`), `L_Act_date2`,
  `file_list` (мотиви — PDF/RTF, без директен download endpoint).
- `/pl-sten/{id}` — стенограма: `Pl_Sten_body` (**пълен текст**),
  `files`: `gv*` (гласувания) + `iv*` (поименни) като `.csv` / `.xlsx` / `.xls`.
- `/archive-period/bg/Pl_StenV/{година}/{месец}/0/0` — стенограми по месец
  (fallback, когато `steno_hall` е празен или `Pl_Sten_id: 1` — чести за стари НС).

### Гласувания — формати по ери
- **CSV** (2018–2025, без 2021-online): ред = тема + партия + бройки.
  Два формата: стар `[..., party, za, pr, vz]` / нов `[..., party, '50', za, pr, vz]`.
- **XLSX** (`gv*.xlsx`, inlineStr): блокове тема → header → `Общо:` → партии
  (колони C=за, D=против, E=въздържали се). Има и за дати без CSV (30.07.2025).
- **XLS** (стар BIFF, 2020–2021): чете се с python `xlrd`.
- **2021-online XLSX**: само цифрови кодове без теми — **нечетим**, не се ползва.
- **iv файлове** (поименни): само първите ~10–16 гласувания за деня — стават за
  сверка, не за пълен вот.
- **Хибридна ера** (зала+онлайн, 47-мо НС): CSV = само зала, обявлението =
  зала+онлайн. Разбивка се пази **само ако сумите съвпадат точно** с обявлението,
  иначе само обявени тотали (`votesVerified: "partial"`).

### Държавен вестник (`dv.parliament.bg/DVWeb`, JSP/JSF, без публично API)
- Материал: `showMaterialDV.jsp?idMat={idMat}` (работи през curl).
- Търсене: `searchDV.faces` (JSF POST: viewstate + `search_form:_idJsp69`=брой +
  `from_date`/`to_date` за година + `btnFind.x/y`; пагинация: `selectPage=N` +
  **`search_form:_idcl=search_form:chP`** — без `_idcl` връща все стр. 1!).
- Началната страница показва само последния брой (+ истински idMat линкове).

## Pipeline-и и скриптове (`scripts/`)

1. **Индекс на актовете** — `enumerate-acts.mjs` (обхожда `/act/{id}`, resumable;
   изход `data/acts-index.json` със slim полета). Седмично: `check-dv.mjs`.
2. **ДВ материали** — `resolve-dv-mat.mjs` (търсене по 348-те броя, 3 worker-а с
   `--out`/`--only`; изход `dv_mat` = истински idMat). Мачване акт→материал по
   заглавие (нормализация + праг 0.9 / 0.7 с gap ≥ 0.2; остатък — ръчно).
3. **Вотове (единични)** — `extract-vote.mjs <ns> <дата> <думи>` (CSV) и
   `extract-vote-xlsx.mjs <stenId> <думи>` (XLSX). Взимат **последния приет** вот
   по темата; кандидатите се печатат в stderr за ръчен преглед.
4. **Вотове (bulk)** — `fetch-act-details.mjs [--out F --only ID...]`:
   bill → стенограми (II, после I) → CSV/XLSX → fallback по дата (`L_Act_date2`,
   после дата от ДВ материала през `dv_mat`) → transcript-totals. Всеки запис:
   `{pick|status, verified: true|"partial"|false, stenIds, kws, vnositel}`.
   Вотът на приемане = **последният непроцедурен вот по темата** — процедурните
   вотове (програма, „процедура за допускане в зала“) също завършват с „прието“
   и кандидат-класацията иначе хваща тях (виж „Вотът на приемане“).
5. **Детайли от bills** — `fetch-basics-bills.mjs` (вносители, сигнатури, вета,
   DV-ID). Вносител без `imp_list` + код `x02`/`002` = МС — потвърждава се с
   „Вносител – МС" от стенограмата, не по аналогия.
6. **Merge** — `upgrade-basics.mjs` (22-те) + ad-hoc python (нормализация на
   партии, сливане на дубликати, `stenogramLink` през дата→НС, mine `dv_mat` →
   `sources.dv`). Партии: `ГЕРБ - СДС`→`ГЕРБ-СДС`, `ПП - ДБ`→`ПП-ДБ`,
   `ДПС - НН`/`ДПС - ДПС`/`ДПС `→`ДПС`, `БСП - ОЛ`→`БСП`, `ВЪЗРАЖДАНЕ`→`Възраждане`,
   `ВЕЛИЧИЕ`→`Величие`, `НЕЧЛ В ПГ`/`НЕЧЛ ПГ`/`НЕЗ`→`независими`; нулевите отпадат.
   Курирано→данни: `merge-curated.mjs [--dry]` (вход `/tmp/curate-merged.json` +
   `/tmp/act-dates.json`) пише в `amendments.json`/`laws.json`: `fullTitle`,
   `dateDV`, `decreeNo`/`dateDecree`, `dateEffective`, `billSignatura` (fallback
   към `sign` от индекса), групиране по родителски закон (`LAW_BY_ACT` за
   изключения като ЗСПР с дългото заглавие), нови law entries със slug/code/
   категория. `dateEffective` се пише само при изрична норма в закона (данъчен
   със задна дата, ратификация „от обнародването“); отложени/частични режими
   („чл. 12–23 след 9 месеца“) НЕ се пишат — пътят в UI показва датата на ДВ.
7. **Сверените детайли → индекс** — `apply-act-details.mjs [--dry]` (вход
   `/tmp/weekly-new-acts.json` + `/tmp/act-picks-override.json` + `/tmp/act-cards.json`)
   пише `votes`/`votesVerified`/`votesByParty` (нормализирани, нулевите редове
   отпадат), `stenogramLink` (НС по датата на вота), `vnositel`/`vnositelType`,
   `detailId`, `card*`. Пише вот само при `verified === true` (скрипт или ръчен
   override) и **спира без запис** при конфликт с вече попълнено поле.
8. **Куриране** — `enrich-details.mjs <actId>` (членове+снипети от ДВ текста);
   пълният текст → `changes[]` (цитати преди/сега + „с прости думи"),
   `summary`, `tags`, `shortTitle`, `billSignatura`, `detailLevel: "full"`.

## Правила за сверка (вотът на приемане)

- Вотът е приемането **само ако**: (а) числата съвпадат дословно с обявление
  „Гласували …" в стенограмата + (б) следва „приет" + (в) стенограмата е ±4 дни
  от приемането. Иначе → карантина (`status: "quarantine*"`), без запис.
- **Процедурен капан** (ИНЦИДЕНТ 10.2026, ДВ 30/2026): по темата има и вотове
  „приемане на процедурата за допускане в зала“ / програма, които също
  завършват с „прието“ и събират същите числа на „за“. Вотът на приемане е
  **последният непроцедурен вот по точката** — иначе pick-ът хваща процедурния.
  След фикса в `fetch-act-details.mjs` скриптът сам изключва процедурните.
- `verified: true` от скрипта = кандидатът мина софтуерните порти; при съмнение
  (обединен вот, преименуван закон, субстринг) всеки вот се сверява ръчно с
  обявлението „Гласували …“ в стенограмата, преди `apply-act-details`.
  Четящият обявлението: тоталите („Гласували: за N, против M, въздържали се K“)
  трябва да съвпаднат точно, не приблизително.
- Една стенограма често съдържа вота на **два закона** (нпр. nk-61/nk-65) —
  затова освен темата се гледа и датата.
- Вот без отделен финал (бърза процедура, §50а / чл. 159): приемането е
  последният параграф — важи само с изрична декларация („С това е приет…").
- Transcript-totals: търси се **в границите на точката** (сегментиране по
  „Преминаваме към…"), последният приет вот + финален маркер
  (`завършваме|закривам|…|приет на второ гласуване|…е приет`). Процедурни
  вотове (удължаване на времето) с еднакви числа иначе заблуждават.
- Вето: `veto: {by, overridden}`; `votes` = вотът на приемане (като ik-23-2026),
  прегласуването след вето се споменава, не се смесва.

## Капани (платено с време)

- `Pl_Sten_id: 1` = липсващ линк (стари НС) → date-search fallback.
- `L_Act_dv_ID` ≠ idMat (брой vs материал) — беше счупило всички ДВ линкове.
- Резервации на колони във flood-fill фрагментират (премахнати).
- Свързаност в залата = по графа на съседите (с мостове ложа–среда 34px),
  не по евклидово разстояние.
- 2021-online файлове и `iv` (първи ~10 вота) не стигат за разбивка.
- JSF пагинацията иска `_idcl=search_form:chP`, иначе връща стр. 1.
- ДВ заглавията имат суфикси („стр. N", `<a id=`) — чистят се преди мач.
- Еднакви заглавия в един брой (3 ваксинални дарения; процедурни правила) —
  различават се по държава/орган, ръчно.

## Седмичен процес (~2 мин автоматично + ръчно куриране)

1. `npm run check:dv -- --json` → нови броеве от ДВ + кои `(година,брой)`
   липсват в индекса + акти с ДВ без `dv_mat` (готово за chaining).
2. `node scripts/enumerate-acts.mjs` (без аргументи: auto-extend от max ID
   до 300 поредни липси — най-дългата наблюдавана дупка е 214) и
   `node scripts/enumerate-acts.mjs --refresh-missing` (препроверка на
   индексирани БЕЗ ДВ от последните ~1500 ID-та; прозорец `--window N`).
   Пребутването пази обогатяванията (`dv_mat` и др.).
3. `node scripts/resolve-dv-mat.mjs --only ГОДИНА,БРОЙ ... --jobs 3`
   за новите броеве от стъпка 1.
4. За всеки нов акт: bill → вот (`fetch-act-details --jobs 3`) → сверка
   (горе) → `changes[]` по текста → merge (`apply-act-details.mjs` за
   вот/вносител/картички в индекса, после `merge-curated.mjs` за курираното —
   винаги `--dry` първо) → build → проверка (суми, баджове, линкове) → push.

## Кодове на вносителите (сигнатури ` {НС}-{код}-...`)

- `x02` / `002` = **Министерски съвет** (потвърдено със стенограми за
  47-202, 49-302, 51-502, 002, 52-602). Единственият код, за който празен
  `imp_list` означава МС.
- `154-02`, `153-*`, `053-*`, `054-*`, `104-*`, `120-*`, `253-*`, `254-02`,
  `353-*`, `453-*`, `554-*`, `654-*` = **депутатски/комисийни** предложения
  (решения, правилници, декларации) — празният `imp_list` там НЕ е МС.
- `x53` / `x54` / `x55` + `union_label` = **обединен законопроект**.
- ИНЦИДЕНТ: bulk скриптът слагаше „МС" на всеки празен `imp_list` → 819 грешни
  реда в индекса + 803 в amendments. Изчистени по код (запазени само x02/002 и
  ръчно сверените с „(кабинет …)"). Правило: `vnositel` се пише само при
  `imp_list` ИЛИ union ИЛИ x02-код, иначе се пропуска (страницата показва
  „предстои" — вярно).

  — проверяват се отделно.

## Куриране в мащаб (закони → решения)

- Worker-и (Task subagents, 4–8 паралелно): вход `{actId, title, dv, dv_mat,
  sign}` → ДВ текст → изход `{shortTitle?, summary, tags, changes[],
  changedMembers[], billSignatura}`. За решения: само summary/tags (без changes).
- Валидационни порти (автоматични, преди merge): непразни after+plain, без
  плейсхолдъри („Създава се нов текст…"), без мета-резюмета („засяга N записа"),
  уникален member, ≤12 записа, 2–4 свързани тага. Един worker беше хванат да
  мързелува (101 плейсхолдъра) — slice-ът му е изхвърлен и преправен.
- Дублирани изходи (мои + външни файлове) → merge по качество (най-богатата
  чиста версия печели).
- Групиране по родителски закон: unwrap на „ЗИД на …" + именителен падеж
  (`-ния кодекс`→`-ен кодекс`) + мапване към съществуващите 6 + strip на години
  (`... за 2024 г.`). Нови law entries: slug (транслитерация), code от инициали,
  категория по ключови думи. Ратификации → един закон `ratifikatsii`; решения →
  7 тематични (`resheniya-komisii/organi/strategii/pravila/finansi/izbori/drugi`).
- `dateAdopted`: от ДВ текста („приет … на …") за всички (един batch, ~10 мин);
  `assemblyId` по диапазони. `feedItems` и `zakoni` сортират null-safe.
- Празен `changes[]` (ратификации/решения) → секция „Какво се промени" се крие
  (template условност), баджът е full.
- Изпуснати от regex-класификация (26: Правилник/Декларация без „Решение",
  „Закон изменение" без „за") → добавени ръчно. Поука: класификацията да се
  тества срещу целия индекс преди batch.

## UI поуки

- Feed на началната: пагинация (30 + „покажи още") — 1500 карти иначе.
- Баджът в `/aktove` е per-act (`actsDetailByBill`: bill ID → `/promeni/[id]`),
  не per-брой — иначе всички актове в един брой светват грешно.
- ДВ линк само при сверен `dv_mat`, иначе plain текст (никога предположения).
- `dateEffective` със задна дата (данъчен от 1.1.): `LegislativePath` показва
  стъпката „Влиза в сила“ с „с обратна сила“ и смята резюмето „От гласуване до
  **обнародване**“ — иначе дните излизат отрицателни (видяно: −71 дни за
  act-166879).
